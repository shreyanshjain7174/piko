<objective>
Give Back Tap and the Action Button the only entry point either can actually reach: a single
`AppIntent` that calls the same `arm()` the in-app button calls. `03-RESEARCH.md` is explicit that
neither trigger has a direct third-party API — Apple's own "Hardware interactions" documentation
confirms both route through Settings-configured App Shortcuts, and this project's own
`docs/CONSTRAINTS.md` C2 (no background-audio-activation exception for App Intents, unlike
CallKit/LiveCommunicationKit/PushToTalk) means the intent almost certainly needs
`openAppWhenRun = true` to legally call into `arm()` at all.

Purpose: this is the phase's highest-uncertainty area — `03-RESEARCH.md` rates the
`openAppWhenRun` requirement MEDIUM confidence (a sound inference from sourced CONSTRAINTS.md, not
yet device-verified) and explicitly recommends it be "the first thing the plan verifies... before
any other Wave 0 work in this phase," which this plan honors by opening with a decision checkpoint
rather than silently picking an approach. Per `docs/WORKING-AGREEMENT.md` item 1, this plan
presents the real options — including the option of NOT building a custom intent at all — before
committing code.
Output: `ArmSessionIntent.swift`, `PikoShortcuts.swift`, and a new manual verification entry in
`docs/SPIKES.md` for the one thing no Simulator or CI run can prove: whether Back Tap and the
Action Button actually invoke this intent, and whether `openAppWhenRun = true` is in fact required
on a real device.
</objective>

  <decision>How should `ArmSessionIntent` satisfy CONSTRAINTS.md C2 for Back Tap / Action Button arming?</decision>
  <context>
    `docs/CONSTRAINTS.md` C2 states only CallKit, LiveCommunicationKit, and PushToTalk may activate
    a recording session from the background — "a Bluetooth button buys no exception." Back Tap and
    the Action Button are both hardware/gesture triggers that invoke an `AppIntent` via a
    Settings-configured Shortcut; neither is on C2's exception list. `03-RESEARCH.md`'s Assumptions
    Log (A1) rates this MEDIUM confidence and explicitly recommends resolving it before any other
    Wave 0 work in this plan, since it is genuinely uncertain whether iOS has since gained a
    narrower App-Intents-specific exception not reflected in the current CONSTRAINTS.md wording.
  </context>
  <options>
    <option id="foreground-intent">
      <name>Custom ArmSessionIntent with openAppWhenRun = true (recommended)</name>
      <pros>Satisfies C2 the same way tapping the app icon does — a real, visible foreground
      transition before `perform()` runs `arm()`. Matches `03-RESEARCH.md`'s Pattern 3 and its
      HIGH-confidence reading of C2's exception list. Requires zero further product-scope
      conversation if it works as expected.</pros>
      <cons>Almost certainly means a brief, visible flash to the Piko app before the microphone
      opens — not the fully invisible "arm without touching the screen" experience Back
      Tap/Action Button arming might imply. This is a genuine, not-yet-device-verified UX
      tradeoff, not just an implementation detail.</cons>
    </option>
    <option id="plain-shortcut">
      <name>No custom intent — bind Back Tap/Action Button to a plain "Open App" Shortcut action</name>
      <pros>Zero code, trivially and unambiguously C2-safe (a real foreground app launch, no
      different from tapping the icon). A legitimate, real fallback per `03-RESEARCH.md`'s
      Alternatives Considered table if Option A's device spike fails outright.</pros>
      <cons>Gives up any chance of a single-gesture "trigger arms it" flow — the user still has to
      tap Arm once the app opens. This may not satisfy the spirit of SESS-02/SESS-03 as literally
      worded ("user can arm a session via Back Tap"), only the letter of "Back Tap does something
      useful."</cons>
    </option>
    <option id="background-intent">
      <name>openAppWhenRun = false, attempt background activation directly (not recommended)</name>
      <pros>Would be the most "magical" experience if it worked — no visible app flash at all.</pros>
      <cons>Directly contradicts CONSTRAINTS.md C2's sourced exception list, which does not
      include App Intents. `03-RESEARCH.md`'s Pitfall 2 predicts this throws or silently fails,
      discovered only on-device, late in the phase. Included here only to name why it is rejected,
      per the working agreement's "what would this look like if the obvious approach were
      forbidden" framing — the obvious-seeming "just don't foreground" approach is the one most
      likely to be the forbidden one here.</cons>
    </option>
  </options>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `ArmSessionIntent` invocation source (Siri, Shortcuts, Back Tap, Action Button) | Any of these can invoke `perform()`, but every one of them requires the user to have deliberately configured the binding in Settings first — there is no way for a third party to remotely trigger this intent |
| `openAppWhenRun = true` foregrounding | This is the sanctioned mechanism for C2 compliance, not a bypass of it — foregrounding the app before `perform()` runs is the same legal path as a manual icon tap |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|--------------|-----------------|
| T-piko03-07 | Spoofing | `ArmSessionIntent` invoked by a Shortcut/Siri/hardware trigger the user did not consciously intend in the moment | accept | Requires the user to have deliberately bound the intent to a trigger in Settings beforehand; `arm()` itself only starts a visibly-indicated (mic icon, Live Activity once Phase 7 lands) capture with no data exfiltration or destructive side effect — low-value target for an attacker, and identical in kind to the risk any Shortcuts-capable app already accepts |
| T-piko03-08 | Elevation of Privilege | `openAppWhenRun = true` foregrounding the app from a background-adjacent hardware trigger | accept | This is the sanctioned, Apple-documented mechanism for satisfying C2 from a Shortcut/intent context, not a privilege escalation introduced by this plan — rejecting `background-intent` (option C above) is exactly what avoids the real elevation-of-privilege risk (attempting unauthorized background audio activation) |
</threat_model>
