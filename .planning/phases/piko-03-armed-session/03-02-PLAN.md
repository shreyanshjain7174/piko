03-RESEARCH.md's reference implementation shape for the real conformer this plan builds (adapt,
do not copy verbatim without verifying the exact `AVAudioSession` userInfo key names against
current Apple documentation per `docs/WORKING-AGREEMENT.md` item 2 — this is presented as a
starting shape, not settled fact):
```swift
public final class AVAudioSessionInterruptionSource: InterruptionSource, @unchecked Sendable {
    public var events: AsyncStream<InterruptionEvent> {
        AsyncStream { continuation in
            let task = Task {
                for await note in NotificationCenter.default.notifications(named: AVAudioSession.interruptionNotification) {
                    guard let typeValue = note.userInfo?[AVAudioSessionInterruptionTypeKey] as? UInt,
                          let type = AVAudioSession.InterruptionType(rawValue: typeValue) else { continue }
                    switch type {
                    case .began: continuation.yield(.began)
                    case .ended:
                        let optionsValue = note.userInfo?[AVAudioSessionInterruptionOptionKey] as? UInt ?? 0
                        let shouldResume = AVAudioSession.InterruptionOptions(rawValue: optionsValue).contains(.shouldResume)
                        continuation.yield(.ended(shouldResume: shouldResume))
                    @unknown default: continue
                    }
                }
            }
            continuation.onTermination = { _ in task.cancel() }
        }
    }
}
```

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `NotificationCenter` `userInfo` payloads from `AVAudioSession`/`ProcessInfo` | OS-supplied, not user/network input, but must still be defensively unwrapped — a malformed or future-OS-version payload must degrade to "ignore this notification," never a crash, per `03-RESEARCH.md`'s Security Domain section |
| Merged three-source `AsyncStream` in `AVAudioSessionInterruptionSource` | Three independent `Task`s writing into one continuation — a bug here (e.g. a `Task` never cancelled on `onTermination`) is a resource leak, not a data-integrity issue, since `InterruptionEvent` carries no sensitive payload |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|--------------|-----------------|
| T-piko03-04 | Denial of Service | `AVAudioSessionInterruptionSource`'s `userInfo` unwrapping across all three notification sources | mitigate | `guard let` + `@unknown default` on every `InterruptionType`/notification payload switch, per Task 1's action — a malformed or future-OS-version payload is ignored, never force-unwrapped |
| T-piko03-05 | Tampering | App Group JSON files (unchanged) | accept | Same carried-forward reasoning as Plan 03-01's T-piko03-02 — this plan reads `channel.readState()` through the same already-hardened path, no new write path introduced |
| T-piko03-06 | Denial of Service | Three concurrent `Task`s per `AVAudioSessionInterruptionSource` instance, one per notification source | mitigate | All three are cancelled via the single `continuation.onTermination` closure when the `AsyncStream` is torn down — mirrors `DarwinChannel.signals`' existing termination-cleanup pattern, preventing a leaked observer Task per instance |
</threat_model>
